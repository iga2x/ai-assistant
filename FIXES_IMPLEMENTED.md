## Completed Fixes (12/20 Issues)

### 1. Pronoun Resolution Double Replacement (Issue 9) ✅
**Problem**: "check that same target" → "check 192.168.1.1 192.168.1.1 target"
**Root Cause**: Patterns `\bthat\b` and `\bsame\b` both matched, causing double replacement
**Solution**:
- Ordered patterns by specificity (most specific first)
- Added cascading replacement check to prevent replacing already-replaced text
- Used `count=1` in `re.sub()` to replace only first occurrence
**File**: `assistant/context/resolver.py`
**Impact**: Correct pronoun resolution in all cases

### 2. Multi-Task Comma Pattern (Issue 7) ✅
**Problem**: "find ip, scan it" not split into multiple tasks
**Root Cause**: Pattern required space before "and/then", didn't handle comma without space
**Solution**:
- Updated regex: `r'(?:\s+(?:and|then)[,\s]+|,\s+(?!and|then))'`
- Improved result combining (shows all tasks, not just last)
**File**: `assistant/app/terminal/pipeline.py`
**Impact**: Multi-task requests work with comma separators

### 3. PersistentShell PTY Marker Collision (Issue 12) ✅
**Problem**: Fixed marker "---END_OF_COMMAND_MARKER---" could appear in tool output
**Root Cause**: Static marker string could be generated by commands
**Solution**:
- Generate unique UUID-based marker per command: `---CMD_END_{uuid}---`
**Files**: `assistant/system/persistent_shell.py`
**Impact**: No marker collisions, reliable command output parsing

### 4. Pending Action Dead Code (Issue 19) ✅
**Problem**: `store_pending_action()` and `has_pending_action()` never called
**Root Cause**: Only `pending_plan` is used, `pending_action` is dead code
**Solution**:

**File**: `assistant/app/terminal/repl.py`
**Impact**: Cleaner code, no dead code

### 6. Safety Gate Creation (Issues 2, 4, 5, 17) ✅

## Phase 6.1: Chat Response Quality - ANALYSIS (Not Yet Implemented)

### Issue Description
For chat/explanation requests like "how to find open ports on my network", the system returns incomplete responses:
- "I'll explain the methods..." (placeholder)
- "Proceeding with: Network Scan" (title only)
- Instead of providing the actual explanation with commands and examples

### Root Cause Analysis

#### Problem 1: Prompt Instructions (assistant/brain/prompt_builder.py)

**PATH A (Chat) - Lines 92-99:**
```json
{
    "content": "A direct answer or friendly response. RULE: If you need to run a command or 'check' something live, you CANNOT use this path. Use Path B instead.",
}
```

**Issues:**
- "A direct answer" is too vague
- The RULE forces AI to Path B for "how to" questions (AI thinks it needs to "check" something)
- Doesn't explicitly say: "PROVIDE FULL EXPLANATION NOW"

**PATH B (Technical Task) - Lines 103-124:**
```json
{
    "content": "Briefly state what you are going to do.",
    "plan": {...}
}
```

**Critical Issue:**
- "Briefly state what you are going to do" = SUMMARY, not full explanation
- For "how to find open ports", AI returns: "I will explain the methods..."
- Then puts actual explanation in plan.steps (which is for EXECUTION, not explanations)
- Result: User sees summary, not the helpful content

#### Problem 2: Intent Classification (assistant/brain/prompt_builder.py)

**Line 85:**
```
4. INTENT CLASSIFICATION: If the user asks "how to" or for an explanation, use PATH A (chat only).
```

**Contradiction:**
- Rule says "how to" = Path A
- But Path A's RULE says "if you need to check something, use Path B"
- AI gets confused: "how to find ports" needs checking → Path B → summary only

#### Problem 3: Missing "Explanation" Intent

Current intents don't have a dedicated category for explanations:
- `CHAT` = general conversation
- `TOOL_HELP` = tool-specific help
- Missing: `CONCEPT_EXPLANATION` or `HOW_TO_GUIDE`

Result: "how to" questions get misclassified as tasks requiring execution.

#### Problem 4: Mock Responses (assistant/ai/mocks.py)

**Lines 22-65:**
- Mock responses ONLY provide `plan`, NO `content`
- When AI follows mock pattern, it returns plan without explanation
- AIResponse.ensure_content() (schemas.py:120-127) generates fallback: "Proceeding with: {title}"
- User sees: "Proceeding with: Network Scan" (not helpful)

```python
def _parse_nmap_discovery(stdout: str) -> Optional[str]:
    """Parse nmap host discovery (nmap -sn) output."""
    if not stdout:
        return None
    
    hosts = []
    for line in stdout.splitlines():
        m = re.search(r'Nmap scan report for\s+([^\s\(\)]+)', line)
        if m:
            hosts.append(m.group(1))
    
    if hosts:
        # Filter out localhost if it's the only result
        if len(hosts) == 1 and hosts[0] in ["127.0.0.1", "localhost"]:
            return "No additional network devices found."
        return f"Discovered devices: {', '.join(hosts)}"
    return None
```

## Phase 6.4: Tool Discovery Unification ✅ IMPLEMENTED (Issue 14)

### Issue Description
Three different tool discovery methods with overlapping responsibilities:
- `detector.py`: Low-level detection
- `registry.py`: Tool discovery and execution
- `manager.py`: Tool management operations

**Problems**:
- Confusing which to use when
- Overlapping responsibilities
- Potential inconsistencies
- No clear "main interface"

### Root Cause Analysis

**Architectural Issue**: No clear separation of concerns
- All three could detect tools
- All three could access metadata
- Unclear which to call from application code
- Potential for inconsistencies

### Implementation

#### Fix 1: Clarified Responsibilities ✅

**Documentation Updates**:

**assistant/tools/detector.py**:
- Added: "INTERNAL USE ONLY" warning
- Added: Architecture documentation
- Added: Migration guide to use ToolRegistry
- Made clear: Low-level function, use via ToolRegistry only

**assistant/tools/registry.py**:
- Added: "MAIN INTERFACE" designation
- Added: Architecture documentation
- Added: Usage examples
- Made clear: Single source of truth for discovery and execution

**assistant/tools/manager.py**:
- Added: "DEPRECATED" warning for discovery/execution
- Added: Architecture documentation
- Added: Migration guide
- Made clear: For lifecycle operations only (install/uninstall/update)

#### Fix 2: Architecture Definition ✅

**Three-Layer Architecture**:

1. **detector.py**: Low-level detection (INTERNAL)
   - Function: `detect_tool(metadata: Dict) -> ToolInfo`
   - Usage: Internal use by ToolRegistry only
   - Responsibility: Pure detection, no side effects

2. **registry.py**: MAIN INTERFACE
   - Class: `ToolRegistry`
   - Methods: `list_available()`, `run_tool()`, `get_tool_info()`
   - Usage: All application code
   - Responsibility: Discovery and execution

3. **manager.py**: Lifecycle operations
   - Class: `ToolManager`
   - Methods: `create_install_plan_for_tools()`, `update_tool()`
   - Usage: Installation and updates only
   - Responsibility: Tool lifecycle management
